# Physical Progress Branch v1

## Purpose

Replace the old clip-end physical-rule MLP with a trainable causal temporal branch.
The branch consumes depth geometry and contact history, then predicts:

- per-frame stage probabilities;
- per-frame local progress;
- globally ordered physical potential in `[0, 1]`;
- stage-entropy confidence;
- pairwise preference `A>B`, `B>A`, or `tie`.

## Model

```text
depth/contact sequence
  -> feature normalization + missing-value indicators
  -> frame MLP
  -> causal GRU
  -> stage head
  -> stage-conditioned local progress head
  -> soft stage routing during training
  -> hard stage routing + conservative completion gate during inference
  -> global physical potential
```

The learned stage selects a fixed interval of the global potential. Local depth
progress moves continuously only inside that interval. The terminal stage is
saturated at `1`. Training uses soft routing for stable gradients; evaluation and
runtime inference use hard routing to enforce the stage bounds.
Stage 4 is accepted only when its predicted probability is at least `0.8`;
otherwise inference falls back to the most likely nonterminal stage. This keeps
an uncertain near-complete state from saturating the reward at `1`.

The training loss contains:

```text
pairwise Bradley-Terry preference loss
+ contact-anchored stage classification loss
+ stage-local progress regression on clean successful trajectories
+ low-weight monotonic loss on clean successful clips
+ independent terminal-window stage/progress loss for every trajectory
```

The stage-local target runs from `0` to `1` within each contact-derived stage.
It is generated only for clean successful trajectories. Failure, truncated, and
near-miss trajectories receive no forced temporal-progress target. Every frame in
the terminal success stage uses target `1`, so holding a completed state does not
create an artificial progress decline.

Checkpoint selection balances pair accuracy, stage accuracy, and stage-local
progress MAE. This prevents an early model with strong pair ranking but unstable
stage predictions from being selected.

Frozen teleport near-misses match the saved video geometry but do not have valid
post-teleport contact force. Their stale contact values are therefore stored as
missing. During training, the corresponding successful trajectory's observable
contact/gripper values are copied in as an adversarial augmentation. The model
must use depth geometry to reject the near-miss even when touch looks successful,
instead of learning the shortcut `missing contact = failure`.

The model input explicitly excludes:

```text
env_success
time_progress
stage_id
task_progress_score_v1
geometry_progress_proxy
physical_score_proxy
candidate/fusion/VLM labels
```

Stage IDs are used only as auxiliary training targets. Pair labels default to the
synthetic pair construction label (`candidate_label`), so the physical branch does
not consume commercial-VLM output. Pair weights default to the construction-side
`candidate_confidence`, rather than the VLM/fusion loss weight.

## Runtime

```python
from physical_progress_branch_v1 import PhysicalProgressRuntime

runtime = PhysicalProgressRuntime.from_checkpoint(
    r"D:\Users\User\Desktop\reward_model_dataset\reward_model_runs"
    r"\physical_progress_branch_v1\best_model.pt"
)

result = runtime.score("stackcube", recent_physical_frames)
comparison = runtime.compare("stackcube", clip_a_frames, clip_b_frames)
```

`recent_physical_frames` is a chronological list of dictionaries. Keep the latest
16 raw frames in this list. Runtime inference matches training by uniformly
sampling 6 frames from that history. Missing values are permitted and are
represented by learned validity indicators.

Run the trajectory and near-miss audit with:

```powershell
python dataset_generation\25_evaluate_physical_progress_branch_v1.py
```

The current checkpoint reaches `1.000` test pair accuracy and `1.000`
hard-negative accuracy. Across all three tasks, clean-success terminal stage-4
recall is `1.000`; failure stage-4 false positives are `0`, including held-out
near-misses with success-like contact injected. These are bootstrap-dataset
results, not an online-policy or out-of-distribution claim.

## Current Boundary

The existing stereo tables are generated by projecting ManiSkill environment state
through a fixed camera model. They validate the model and data interface, but they
are not real stereo estimates. Before observation-only experiments, replace those
columns with features extracted from SGBM, RAFT-Stereo, IGEV-Stereo, or another
stereo backend while keeping the same feature names and units.

The contact extractor now supports left/right finger contact, both-finger contact,
gripper width, and grasp confirmation. The current contact CSV files were
regenerated with these fields. Dynamical trajectories have real ManiSkill/SAPIEN
contact queries; frozen teleport near-misses explicitly mark contact unavailable.
